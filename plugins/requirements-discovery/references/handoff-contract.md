# Specification input contract

Handoff publishes the current reasoning state as two files:

- `.requirements/handoff.md`: Markdown rendered by the helper from the graph, with labels in the user's language and the agent's branch conclusions, and a draft banner when blocked.
- `.requirements/handoff.json`: publication metadata (schema 3), containing discovery identity, revision, status, timestamp, graph/body/metadata hashes, the renderer version, the language and conclusions that reproduce the Markdown, blockers, audit request and the semantic review with any audit report. A schema 2 publication carries a prose body without render inputs; the helper reads it like any other publication.

The Markdown contains no generated metadata frontmatter. JSON keeps the render inputs, not a copy of the rendered Markdown. Both files form one publication and are required for readiness. Handoff is input for Spec Kit, not the specification, research transcript or implementation plan.

## The rendered document

The document has a title, the recorded intent and scope, constraints, facts, the questions and decisions as a tree from the root issue, assumptions, retired nodes still referenced, and an index of open questions. Each node shown with its text is rendered exactly once, at its home, as `**[ID]**` with its verbatim text, status, editorial hint, custom tags, sources, causal links, the relations it has with shown nodes, and every further metadata field; elsewhere it is referenced as `[ID]`. A decision sits under the first current issue it resolves, with its rationale, basis, reviews and consequences; a factual resolver sits under the question it answers. Recorded text is escaped for Markdown, so it displays literally.

The helper derives four classes from the shared status lifecycle (`LIFECYCLE` in the graph module) and the operative closure that mechanical readiness uses:

- **Current:** every node whose status is not retired, except options of decided questions that were not chosen; reviews of current decisions that a later review did not replace; arguments that a current node relies on or that bear on a current node. A retired node never becomes current. Rendered verbatim.
- **Retained:** retired nodes that the operative state still relies on. They block readiness, so they are shown with their text and their referrers in their own section.
- **History:** earlier versions (`superseded_by`), earlier resolutions of a question, earlier reviews, consequences of earlier decisions, and the original basis of a reaffirmed decision and of the options it selects. Listed by ID beside their record.
- **Not chosen:** everything else, such as unselected options of decided questions, dropped questions and reasoning about those options. Never rendered as text, only through a conclusion that lists its IDs.

A conclusion is `{issue, covers, text}`, written by the agent at handoff time. `issue` is the current issue where it is shown, `covers` lists the nodes of one abandoned branch, and `text` is a short self-contained judgment (at most 2000 characters) of what was explored and why it was not taken. A conclusion may also fold current reasoning, facts, proposed constraints and fact-answered questions of the same branch, but only a closed branch: nothing folded may be a commitment or blocker of the projection (`required_coverage`), be depended on by a node that stays shown, bear on a node that stays shown, be a question outside the conclusion's issue, or lack a link to the rest of what the conclusion covers. A dropped question concludes itself and its attached options and arguments with its recorded `reason`. Metadata notes keyed by nodes that were not chosen, such as per-option rejection reasons, keep only those IDs. Malformed input fails with `INPUT`, conclusions that do not fit the graph with `CONCLUSION`, and a branch left without a conclusion with `COVERAGE`.

The helper guarantees that every graph ID is placed in the document, that shown texts are quoted verbatim, that every node not chosen is concluded, that folding hides no commitment, and that the same graph, language and conclusions render the same bytes; `RENDERER` changes when they would not. Labels exist for `en` and `uk`; other language tags are refused. Conclusions add no FR numbering, stories, acceptance criteria, API design, task lists or plans, and do not turn uncertain facts, conditional preferences or superseded commitments into approved intent. Follow `semantic-review.md` before publication.

## Mechanical and semantic readiness

`project` reports **mechanical** readiness. It checks known blocking Issues, Assumptions, challenged commitments, current causal dependencies and factual closures. Shared/deep dependencies are traversed iteratively; circular operative justification is blocked. A root container may remain open, but at least one product Decision must establish target behavior. Factual answers alone are insufficient.

Publication also needs a recorded semantic review of the actual rendered draft and graph. Run `handoff-preview` with `{language,conclusions}` to obtain their hashes and an unfilled review template; `render` with the preview's graph hash as `--expect` prints exactly that draft. The template's sources are those of every node shown with its text, together with those the projection relies on; the same inventory is used for the local snapshot checks. Review five axes and account for current source pointers; fill the template with concrete observations, then publish `{language,conclusions,review}`. The receipt refers to the pre-publication graph; `handoff.json`'s graph hash seals the next lifecycle revision. Changing the graph, language or conclusions requires a fresh review/preview.

All five checks need `pass | blocked` and a substantive note. Each source needs `checked | not-needed | unavailable` with a reason. `not-needed` must explain why source reinspection is unnecessary (e.g. current user intent, immaterial rejected option); it is not a bypass for an unknown material contract. Missing review, blocked findings or unavailable material sources result in a blocked draft. Malformed/stale review input is rejected. Local file pointers with a recorded `sha256` are rechecked at preview, publication and `handoff-status`; changed or unavailable snapshots block readiness. URLs are not fetched by the helper.

The receipt makes the review explicit and traceable. It **does not prove** that the model assessed the conclusions correctly or that agreement exists. The helper checks recorded results, hashes and the structure of conclusions, not natural-language meaning. No mandatory second model is called; an independent read-only audit is optional on explicit user request. Never mark pass just because the graph parses or IDs are present.

An explicitly requested audit is gated, not merely advisory logging: follow `independent-audit.md`, prepare actual snapshots and launch a new restricted custom agent after concluding the branches. Record `review.independent_audit`, bound to both preview hashes. Missing/unavailable reports and unresolved blocking findings prevent ready publication; malformed/stale reports are rejected. Preserve the original report and any evidence-backed main-agent `audit_responses`. A supplied report participates even if audit_requested is false. An independent pass never overrides the main semantic review, mechanical blockers, source currency or missing product intent.

## Publication and currency

Coverage is structural: the helper references every graph ID and refuses a draft with a branch left unconcluded. Structural coverage is necessary but insufficient; semantic review verifies that the verbatim texts are understandable and that every conclusion is faithful. Known blocking state cannot be overridden by a pass receipt or a conclusion.

Ready publication moves discovery to `handed-off`. A blocked publication carries a prominent draft banner and retains the prior lifecycle. It is never approved Spec Kit input. Under the writer lock, publication renders the body again and atomically writes `handoff.md`, then `handoff.json`, then the next graph for ready input. Hash bindings detect incomplete or mismatched publications. Each handoff file is limited to 4 MiB. `body_sha256` hashes the exact Markdown bytes; `metadata_sha256` hashes canonical JSON excluding that hash field. Missing or unreadable files fail freshness. Manual changes or later lifecycle/reasoning updates invalidate currency. Archive and Position reconciliation preserve both files. The helper returns `file` for Markdown and `metadata_file` for JSON. Hashes protect freshness, not authenticity against a deliberate local writer.

External source changes without a recorded local snapshot hash require agent reinspection. A current document's hashes do not certify external truth or complete domain coverage. `handoff-status` exits nonzero unless the reviewed document is current, mechanically ready and has no changed recorded local source snapshots. Its `reproduction` field reports whether the graph and recorded inputs still render the published bytes: `reproducible`, `differs`, `renderer-changed` (a newer renderer), `not-renderable` (the recorded conclusions do not fit the current graph), `legacy-prose` (a schema 2 prose body) or `unreadable`. Reproduction is a diagnostic, not part of readiness, so a plugin update does not invalidate a ready handoff.

Only the user's subsequent request invokes `/speckit.specify`. Spec Kit remains responsible for specification writing; the plugin never installs or reconfigures it.
